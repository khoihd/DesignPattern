MODERN SOFTWARE PATTERNS & ARCHITECTURE — EXTENDED STUDY ROADMAP
============================================================

Purpose: Continue beyond the original Gang of Four (GoF) tutorial.
Level 0: Original 23 GoF lessons, numbered 0.1–0.23.
Start of new material: Lesson 1.1 — Dependency Injection.
Numbering: Level.Topic; topic numbering restarts at 1 in each level.

SCOPE AND CLASSIFICATION
- This is a proposed study curriculum, not an official or exhaustive
  standardized catalog of every software pattern.
- The topics cover design patterns, architectural styles, concurrency
  models, distributed-systems techniques, and operations practices.
- Related topics are grouped together, but each topic is listed once.
- Keep the existing nine-part lesson structure: introduction, initial
  design, its limitations, step-by-step solution, runnable Python,
  walkthrough, related concepts, tradeoffs, and an optional exercise
  with a complete solution.
- Preferred examples: backend systems, distributed task scheduling,
  databases, messaging, caching, networking, and fault tolerance.

LEVEL SUMMARY
0. ORIGINAL GANG OF FOUR (GOF) PATTERNS: 23 topics (0.1–0.23)
1. CORE APPLICATION AND SYSTEM DESIGN: 33 topics (1.1–1.33)
2. ESSENTIAL DISTRIBUTED-SYSTEMS PATTERNS: 42 topics (2.1–2.42)
3. ADVANCED ARCHITECTURE AND OPERATIONS: 12 topics (3.1–3.12)
Total: 110 topics across Levels 0–3; 87 new topics in Levels 1–3.

The first six Level 1 topics (1.1–1.6) preserve the previously agreed order.
Subsequent topic numbers below are proposed and can be adjusted.

LEVEL 1 — CORE APPLICATION AND SYSTEM DESIGN
========================================================================

Foundational patterns (agreed next six lessons)
-----------------------------------------------
Lesson 1.1. Dependency Injection
    Type: Design technique
    Goal: Supply dependencies from outside a component to reduce coupling and improve tests.
Lesson 1.2. Repository
    Type: Data-access pattern
    Goal: Provide a persistence abstraction between domain logic and storage.
Lesson 1.3. Model-View-Controller (MVC)
    Type: Architectural pattern
    Goal: Separate data/application behavior, presentation, and input coordination.
Lesson 1.4. Event-Driven Architecture (EDA)
    Type: Architectural style
    Goal: Decouple components through the publication and handling of events.
Lesson 1.5. Actor Model
    Type: Concurrency model
    Goal: Represent independent stateful actors that communicate through messages.
Lesson 1.6. Orchestrator-Worker
    Type: Coordination pattern
    Goal: Assign and coordinate tasks across multiple workers.

Application structure and boundaries
------------------------------------
Lesson 1.7. Inversion of Control (IoC)
    Type: Design principle
    Goal: Move control of dependency creation or execution outside a component.
Lesson 1.8. Service Layer
    Type: Application pattern
    Goal: Offer a clear boundary for application operations and workflows.
Lesson 1.9. Data Transfer Object (DTO)
    Type: Data-transfer pattern
    Goal: Carry data across process or architectural boundaries.
Lesson 1.10. Domain Model / Aggregate
    Type: Domain-design concepts
    Goal: Model domain behavior and enforce consistency boundaries.
Lesson 1.11. Unit of Work
    Type: Persistence pattern
    Goal: Track and commit a set of related persistence changes together.
Lesson 1.12. Data Mapper
    Type: Persistence pattern
    Goal: Keep object-domain models independent of database representation.
Lesson 1.13. Model-View-ViewModel (MVVM)
    Type: Presentation pattern
    Goal: Separate UI state/presentation logic from views.
Lesson 1.14. Hexagonal Architecture (Ports and Adapters)
    Type: Architectural style
    Goal: Use ports and adapters to isolate domain logic from external systems.
Lesson 1.15. Clean Architecture
    Type: Architectural style
    Goal: Keep dependency direction centered on application/domain logic.

Service and application architecture
------------------------------------
Lesson 1.16. Modular Monolith
    Type: Architectural style
    Goal: Enforce modular boundaries inside one deployable application.
Lesson 1.17. Microservices Architecture
    Type: Architectural style
    Goal: Compose systems from independently deployable services.
Lesson 1.18. Decomposition by Business Capability / Subdomain
    Type: Service-boundary strategy
    Goal: Identify cohesive service boundaries around business capabilities.
Lesson 1.19. API Gateway
    Type: Gateway pattern
    Goal: Provide a single client-facing entry point to backend services.
Lesson 1.20. Backend for Frontend (BFF)
    Type: API architecture pattern
    Goal: Expose APIs adapted to the needs of different clients.
Lesson 1.21. Strangler Fig
    Type: Migration pattern
    Goal: Replace legacy functionality incrementally.
Lesson 1.22. Anti-Corruption Layer
    Type: Integration pattern
    Goal: Translate external models without contaminating the domain model.

First distributed building blocks and operations
------------------------------------------------
Lesson 1.23. Publish-Subscribe
    Type: Messaging pattern
    Goal: Broadcast events to independently interested subscribers.
Lesson 1.24. Point-to-Point / Work Queue
    Type: Messaging pattern
    Goal: Distribute tasks through a queue to one consuming worker per delivery.
Lesson 1.25. Request-Reply
    Type: Messaging pattern
    Goal: Associate a response with a request across a messaging boundary.
Lesson 1.26. Worker Pool
    Type: Concurrency pattern
    Goal: Bound and distribute parallel task execution among workers.
Lesson 1.27. Fan-Out / Fan-In
    Type: Parallel-processing pattern
    Goal: Dispatch parallel work and merge results.
Lesson 1.28. Cache-Aside
    Type: Caching pattern
    Goal: Load data into cache on misses and explicitly manage invalidation.
Lesson 1.29. Timeout and Deadline
    Type: Resilience technique
    Goal: Limit how long operations and end-to-end requests can run.
Lesson 1.30. Rate Limiting
    Type: Traffic-control pattern
    Goal: Constrain request throughput to protect resources.
Lesson 1.31. Health Endpoint Monitoring
    Type: Operations pattern
    Goal: Expose health signals to detect and respond to failures.
Lesson 1.32. Feature Flags
    Type: Release technique
    Goal: Control feature activation separately from deployment.
Lesson 1.33. Externalized Configuration
    Type: Configuration pattern
    Goal: Keep environment-specific configuration outside application code.

LEVEL 2 — ESSENTIAL DISTRIBUTED-SYSTEMS PATTERNS
========================================================================

Messaging, routing, and delivery semantics
------------------------------------------
Lesson 2.1. Competing Consumers
    Type: Messaging pattern
    Goal: Scale queue processing with multiple consumers.
Lesson 2.2. Asynchronous Request-Reply
    Type: Messaging pattern
    Goal: Accept requests now and make results available later.
Lesson 2.3. Correlation Identifier
    Type: Messaging pattern
    Goal: Link replies and events to the originating operation.
Lesson 2.4. Content-Based Router
    Type: Messaging pattern
    Goal: Choose destinations according to message contents.
Lesson 2.5. Pipes and Filters
    Type: Processing pattern
    Goal: Compose processing from independently reusable stages.
Lesson 2.6. Splitter
    Type: Messaging pattern
    Goal: Split a composite message into smaller messages.
Lesson 2.7. Aggregator
    Type: Messaging pattern
    Goal: Combine multiple related messages or partial results.
Lesson 2.8. Scatter-Gather
    Type: Messaging pattern
    Goal: Broadcast requests to recipients and gather responses.
Lesson 2.9. Dead Letter Queue
    Type: Messaging pattern
    Goal: Isolate messages that cannot be handled successfully.
Lesson 2.10. Idempotent Consumer
    Type: Messaging reliability pattern
    Goal: Make duplicate deliveries safe to process.
Lesson 2.11. Transactional Outbox
    Type: Persistence-messaging pattern
    Goal: Reliably publish events associated with database changes.
Lesson 2.12. Claim Check
    Type: Messaging pattern
    Goal: Store large message contents separately and pass a reference.

Service communication and worker coordination
---------------------------------------------
Lesson 2.13. Service Discovery
    Type: Service architecture pattern
    Goal: Find healthy instances of a changing service.
Lesson 2.14. Sidecar
    Type: Deployment pattern
    Goal: Attach auxiliary service functionality alongside an application.
Lesson 2.15. Leader Election
    Type: Distributed coordination pattern
    Goal: Choose one process to serve as coordinator or leader.
Lesson 2.16. Leader-Follower
    Type: Replication/coordination pattern
    Goal: Organize components around a primary leader and followers.
Lesson 2.17. Lease and Heartbeat
    Type: Coordination technique
    Goal: Track liveness and time-limited resource ownership.
Lesson 2.18. Scheduler-Agent-Supervisor
    Type: Distributed workflow pattern
    Goal: Assign scheduled work, execute through agents, and supervise outcomes.
Lesson 2.19. Work Stealing
    Type: Scheduling pattern
    Goal: Let idle workers pull tasks from busier workers.

Resilience and backpressure
---------------------------
Lesson 2.20. Retry with Exponential Backoff and Jitter
    Type: Resilience pattern
    Goal: Retry transient failures while avoiding synchronized retries.
Lesson 2.21. Circuit Breaker
    Type: Resilience pattern
    Goal: Temporarily stop calls to failing dependencies.
Lesson 2.22. Bulkhead
    Type: Resilience pattern
    Goal: Isolate resource pools to contain failures.
Lesson 2.23. Load Shedding
    Type: Overload-control technique
    Goal: Reject lower-priority or excess work when overloaded.
Lesson 2.24. Queue-Based Load Leveling
    Type: Load-management pattern
    Goal: Buffer sudden request spikes behind a queue.
Lesson 2.25. Fallback
    Type: Resilience technique
    Goal: Offer an alternate behavior when the primary path fails.
Lesson 2.26. Graceful Degradation
    Type: Resilience principle
    Goal: Maintain reduced functionality under partial failure.
Lesson 2.27. Failover and Redundancy
    Type: Availability architecture
    Goal: Use redundant capacity and switch away from failed components.

Data ownership, consistency, and transactions
---------------------------------------------
Lesson 2.28. Database per Service
    Type: Microservice data pattern
    Goal: Assign independent ownership of persistence to each service.
Lesson 2.29. Command Query Responsibility Segregation (CQRS)
    Type: Data architecture pattern
    Goal: Separate read and write responsibilities or representations.
Lesson 2.30. Saga
    Type: Distributed transaction pattern
    Goal: Coordinate multi-service transactions as local steps.
Lesson 2.31. Compensating Transaction
    Type: Distributed transaction technique
    Goal: Semantically counteract committed operations.
Lesson 2.32. Read-Through Cache
    Type: Caching pattern
    Goal: Retrieve missing values through a cache's loading mechanism.
Lesson 2.33. Write-Through / Write-Behind Cache
    Type: Caching patterns
    Goal: Coordinate cache writes synchronously or asynchronously with storage.
Lesson 2.34. Sharding
    Type: Data partitioning technique
    Goal: Distribute partitions of data over multiple nodes.
Lesson 2.35. Primary-Replica Replication
    Type: Replication architecture
    Goal: Replicate data from a primary to one or more replicas.
Lesson 2.36. Optimistic Concurrency Control
    Type: Concurrency technique
    Goal: Detect conflicting updates before committing changes.
Lesson 2.37. API Composition
    Type: Data aggregation pattern
    Goal: Combine information from multiple services at query time.

Deployment and verification
---------------------------
Lesson 2.38. Blue-Green Deployment
    Type: Deployment strategy
    Goal: Switch between two separate deployment environments.
Lesson 2.39. Canary Deployment
    Type: Deployment strategy
    Goal: Roll out to a controlled subset before wider adoption.
Lesson 2.40. Rolling Deployment
    Type: Deployment strategy
    Goal: Update instances incrementally while serving traffic.
Lesson 2.41. Distributed Tracing
    Type: Observability technique
    Goal: Track an operation across service boundaries.
Lesson 2.42. Consumer-Driven Contract Testing
    Type: Testing practice
    Goal: Check providers against requirements expressed by consumers.

    Type: Messaging pattern
    Goal: Restore required order among related messages.
Lesson 3.2. Sequential Convoy

Advanced distributed computation and coordination

    Type: Distributed computation model
    Goal: Map large datasets into parallel tasks and reduce intermediate results.
Lesson 3.4. Distributed Lock with Fencing Tokens
    Type: Distributed coordination pattern

Advanced storage and data processing

Lesson 3.5. Event Sourcing
    Type: Data architecture pattern
    Goal: Represent state changes as an append-only event history.
Lesson 3.6. Materialized View
    Type: Data architecture pattern
    Goal: Maintain precomputed representations for efficient queries.
Lesson 3.7. Consistent Hashing
    Type: Data placement technique
    Goal: Reduce key movement when nodes join or leave.
Lesson 3.8. Transaction Log Tailing
    Type: Change-data-capture technique
    Goal: Extract database changes from a transaction log.

Advanced service infrastructure
-------------------------------
Lesson 3.9. Service Mesh
    Type: Service infrastructure architecture
    Goal: Provide service-to-service traffic and security capabilities.
Lesson 3.10. Ambassador
    Type: Service proxy pattern

Advanced reliability and operations

HOW TO USE THIS ROADMAP
========================================================================
0. Refer to Level 0 (0.1–0.23) for the original GoF lessons.
1. Work through Level 1 to build the application architecture foundation.
2. Use Level 2 to study realistic distributed message processing, data
   consistency, resilience, and deployment concerns.
3. Use Level 3 for advanced coordination, infrastructure, and data models.
4. Favor runnable standard-library Python demos; add third-party systems
   (message brokers, databases, etc.) only when their behavior is central.
5. Distinguish a conceptual design pattern from a complete production system.
6. Review tradeoffs and scenarios where each topic is unnecessary.

End of roadmap.
